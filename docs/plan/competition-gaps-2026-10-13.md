# ช่องโหว่ก่อนส่งงาน AI Builder Cup 2026 (13 ต.ค. 2026)

เหลือ 5 วันก่อนส่ง (18 ต.ค.) เอกสารนี้ประเมิน build ปัจจุบันบน branch `feat/ai-decider` (874c8ee) เทียบกับเกณฑ์ตัดสิน และเสนอ storyboard วิดีโอ 3 นาทีที่ใช้เฉพาะฟีเจอร์ที่มีอยู่ในโค้ดจริง

## สรุป

ส่วนที่อ่อนที่สุดสำหรับคะแนน Technical Merit & Gen AI (40%) คือ **ยังไม่มีหลักฐานว่า Gemini ทำงานได้ดีจริง** ตัว agent มีโครงที่ดี (function calling 7 tools, guardrail จากแกน deterministic, fallback) แต่ HANDOFF บอกว่ายังไม่เคยรันกับ Gemini จริง และไม่มีตัวเลขวัดผลให้กรรมการเห็น ส่วนที่อ่อนที่สุดสำหรับวิดีโอคือ **เรื่องเชิงรุก (Calendar → แจ้งเตือนก่อนถาม) ซึ่งเป็นแกนของ positioning ยังไม่ต่อถึงแอป** API มี `/v1/ingest`, `advise`, `jobs` แล้ว แต่แอปไม่ได้เรียก และการแจ้งเตือนเป็นแค่ log

งานที่ทำไปในรอบนี้: เพิ่ม scorecard ของ agent (`api/internal/agenteval`, `go run ./cmd/scorecard`) ที่ให้ agent ตัดสิน 19 เคสของพายุ demo แล้วตรวจกับแกน deterministic 8 ข้อ รวมถึงตรวจว่าเวลา HH:MM ที่ Gemini เขียนมาจากข้อมูลจริง และมี Gemini judge ให้คะแนนภาษาไทย (structured output) ใช้ได้ทั้ง offline (ตรวจ fallback ผ่าน 19/19) และกับ Gemini จริงเมื่อมี key

## ช่องโหว่เรียงตามผลต่อคะแนน

### 1. ไม่มีหลักฐานว่า Gemini ตัดสินใจได้ถูกและพูดไทยเป็นธรรมชาติ (Gen AI 40%)

ทุก test ใช้ fake model ถ้า Cloud Run ไม่มี key หรือ Gemini ตอบพัง แอปจะได้ `generated_by: "fallback"` โดยที่หน้าจอดูเหมือนเดิม กรรมการจะเห็นแค่ข้อความ template ไม่ใช่ Gemini

- ความพยายาม: ครึ่งวัน (คนที่มี key)
- คำแนะนำ: รัน `GEMINI_API_KEY=... go run ./cmd/scorecard -judge -json score.json` ปรับ `systemPrompt` ใน `api/internal/agent/decide.go` จนผ่านทุก check และ judge ≥ 4/5 แล้วเอาตาราง scorecard ใส่ proposal เป็นหลักฐาน ("19 สถานการณ์ ไม่มีคำแนะนำที่ส่งคนลงน้ำลึกเลย, ทุกเวลาที่ AI พูดตรวจกับข้อมูลได้") ตรวจด้วยว่า revision ที่ deploy มี secret `GEMINI_API_KEY` และ `/v1/decide` ตอบ `generated_by: "gemini"` ก่อนถ่ายวิดีโอ วัด latency ด้วย ถ้าเกิน 5 วินาทีต้องมีสถานะรอบนหน้าจอ

### 2. เรื่องเชิงรุก (Calendar/Gmail → แจ้งก่อนถาม) ยังไม่ต่อถึงแอป (Problem/Innovation 50%, วิดีโอ beat แรก)

`/v1/ingest` ให้ Gemini สกัดนัดจากข้อความ Calendar/Gmail แล้ว resolve เป็นทริปได้แล้ว และมี `advise.Evaluator` ที่ตัดสินแล้วส่งแจ้งเตือน แต่ `notify` มีแค่ `LogNotifier`/`MemoryNotifier` แอปไม่มี Firebase Messaging และ `app/lib/api.dart` ไม่ได้เรียก ingest เลย Calendar/Gmail จริงก็ยังไม่ได้ต่อ

- ความพยายาม: 1 วันสำหรับเวอร์ชันวิดีโอ, 2–3 วันถ้าจะต่อ FCM จริง
- คำแนะนำ: ไม่ต้องต่อ OAuth จริงก่อนส่ง ทำ "วางอีเมลยืนยันตั๋ว/นัดลงไป" ในแอป → `POST /v1/ingest` → แสดงผล extraction (Gemini อ่านเวลา สถานที่) → เปิด verdict ของทริปนั้น เพิ่มใน `api.dart` แค่เมธอด `ingest(title, body, source)` และ model `IngestResponse` ส่วน UI ให้ทีมที่ดูแลหน้าจอเพิ่มปุ่มเดียว สำหรับ push 16:10 ในวิดีโอใช้ local notification ที่แอปยิงเองจากผล `/v1/decide` พร้อมบอกตรง ๆ ใน proposal ว่า production จะใช้ FCM ผ่าน `jobs` scheduler

### 3. Guardrail ตรวจแค่ verdict กับ leave_by ไม่ได้ตรวจข้อความ (Gen AI, ความน่าเชื่อถือ)

`applyAgent` บังคับ `leave_by` จากแกน แต่ headline/summary ที่ Gemini เขียนยังอาจมีเวลาที่ไม่ตรง เช่น headline "ออกก่อน 16:30" ขณะที่ `leave_by` = 16:45 ซึ่ง `applyAgent` จะส่งให้ผู้ใช้ตามนั้น scorecard จับกรณีนี้ได้แล้วในขั้นวัดผล แต่ตอนรันจริงยังไม่จับ

- ความพยายาม: 2–3 ชั่วโมง
- คำแนะนำ: ย้ายฟังก์ชัน `groundedTimes` ของ scorecard ไปใช้ใน `applyAgent` ด้วย ถ้า headline/summary มีเวลาที่ไม่มีในข้อมูล ให้ใช้ข้อความของแกนแทน แล้วบันทึกใน reasoning ว่า "guardrail: เวลาไม่ตรงข้อมูล" เป็นเรื่องที่เล่าในวิดีโอได้ดี ("AI ห้ามแต่งตัวเลข") และควรเปลี่ยนคำตอบสุดท้ายของ agent ให้ใช้ `ResponseSchema` (รอบสุดท้ายแบบไม่มี tools) แทนการให้ตอบ JSON ผ่าน prompt

### 4. รายงานรูปน้ำท่วมยังไม่ถูกใช้แบบ AI เต็มที่ และ fallback ของ vision เป็นค่าคงที่

ถ้าไม่มี Gemini ทุกรูปได้ "20–25 ซม. 84%" เสมอ การกระจายไปหาคนบนเส้นทางเดียวกันเป็นแค่ตัวเลข `notified_users` (27 คน ข้อมูลจำลอง) ไม่มีข้อความที่ Gemini สรุปจากหลายรายงานให้คนที่กำลังจะผ่านจุดนั้น

- ความพยายาม: 1 วัน
- คำแนะนำ: ก่อนส่งให้ยืนยันว่า vision บน Cloud Run ใช้ Gemini จริงด้วยรูปที่จะถ่ายในวิดีโอ ถ้ามีเวลาเหลือ เพิ่ม `GET /v1/reports/summary` ให้ Gemini สรุปรายงานใกล้เส้นทาง ("3 คนรายงานน้ำ 15–25 ซม. ที่รัชดา–ลาดพร้าว ใน 15 นาทีที่ผ่านมา มอไซค์ห้ามผ่าน") และในโหมด live ให้ fallback ตอบว่า "ประเมินไม่ได้" แทนค่าคงที่

### 5. Endpoint ภายในเปิดสาธารณะบน Cloud Run (ความเสี่ยงค่าใช้จ่ายระหว่างตัดสิน)

`deploy/cloudrun.sh` และ `cloudrun.ps1` deploy ด้วย `--allow-unauthenticated` และ `/internal/pubsub/raw`, `/internal/tasks/check`, `/v1/ingest` ไม่มีการตรวจสิทธิ์ ใครก็ยิงให้เรียก Gemini ได้

- ความพยายาม: 1–2 ชั่วโมง
- คำแนะนำ: ปิด route `/internal/*` เมื่อ `DEMO_MODE=0` หรือให้ตรวจ header ลับจาก env ก่อน และตั้ง budget alert ใน project

### 6. โหมดน้ำท่วมยังเป็น rules ล้วน

`homestatus` ไม่ใช้ Gemini เลย ทั้งที่ beat สุดท้ายของวิดีโอเป็นช่วงที่อารมณ์สูงสุด

- ความพยายาม: ครึ่งวัน
- คำแนะนำ: ให้ Gemini เรียบเรียง checklist จากข้อมูลคลอง ฝน และรายงานใกล้บ้าน โดยรายการและลำดับยังมาจาก rules (แบบเดียวกับ agent) ทำเฉพาะถ้าข้อ 1–3 เสร็จแล้ว

### 7. ข้อความใน proposal/docs ไม่ตรงกับโค้ด

`CONTEXT.md` พูดถึง "Gemini 1.5 Reasoner" และ BMA flood spot 70+ จุด แต่โค้ดใช้ `gemini-2.5-flash` และไฟล์มีจุดเสี่ยงแค่ 8 จุด WeatherNext ผ่าน BigQuery ยังไม่ยืนยันสิทธิ์เข้าถึง และ scorecard พบว่าเวลา 19:30 ที่ HANDOFF เขียนว่า "รอถึง 20:00" นั้น API จริงตอบ "เปลี่ยนไปนั่งรถไฟฟ้า" เพราะรายงานที่ seed ไว้ (18:41, 18:47 ที่รัชดา) ยังอยู่ใน 60 นาที ซึ่งไม่กระทบวิดีโอเพราะแอปใช้ preset 16:10/18:52/21:40 แต่ห้ามพูดใน voice-over ว่า 19:30 ให้รอ

- ความพยายาม: 1–2 ชั่วโมง
- คำแนะนำ: แก้ตัวเลขใน proposal ให้ตรงโค้ด ติดป้าย "ข้อมูลจำลอง" ทุกตัวเลขของ scenario และบอกข้อจำกัดข้อมูลตรง ๆ กรรมการให้คะแนนความซื่อตรงมากกว่าตัวเลขสวย

### 8. ถามต่อเนื่องเป็นบทสนทนายังไม่ได้

คำถามแต่ละครั้งตีความแยกกัน แต่แอปส่ง `trip_id` เดิมกลับมา จึงพอเล่าเป็น "ถามต่อ" ได้แล้วในวิดีโอ ไม่คุ้มทำเพิ่มก่อนส่ง
